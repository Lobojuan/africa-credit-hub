# NPL Case Ledger and Exposure Waterfall

## Purpose

The ledger provides a facility-level, append-only chronology for controlled NPL remediation work. It references the existing `credit_accounts`, borrower and optional Collections assignment. It does not create another loan book or another collections queue.

## Case boundary

A case can open only for an authorised facility that has positive exposure and meets a controlled entry signal: at least 30 days in arrears, a delinquent/default/restructured/written-off status, or a mapped non-performing classification. The account's current balance and currency become the opening projection and cannot be supplied by the browser.

One case is permitted per credit account. UCH automatically links the active Collections assignment when one exists.

## Immutable observed events

The first `case_opened` event is generated by the server. Staff may append:

- observed NPL inflow;
- observed cash recovery;
- observed legal recovery;
- workflow-stage change;
- linked Collections activity; or
- a case note.

Financial and Collections-link events require an evidence reference. Events cannot be future-dated or inserted before the latest event. Exposure is calculated by the server with exact two-decimal arithmetic; a recovery cannot exceed the current case exposure. A PostgreSQL trigger rejects every update or delete to `npl_case_events`. Corrections are appended as new evidence.

These event names intentionally say **observed**. The governed decision workspace described below can authorise a cure/re-age, restructure or write-off proposal, but approval still does not post to the credit account, IFRS 9 engine, provision or general ledger.

## Governed remediation decisions

Each case links to a dedicated maker-checker workspace for restructuring, cure/re-age and write-off proposals. A proposal requires a policy/committee mandate, source evidence, rationale and proposed effective date. Write-off proposals require a positive amount no greater than current case exposure; cure/re-age proposals cannot carry an amount.

The maker cannot act as checker. Approval or rejection and later execution evidence are appended to the immutable case chronology without changing exposure. After an approved action is executed in the bank's authoritative system, staff record the bank evidence reference and then reconcile the credit account, IFRS 9, provision and GL outputs separately.

## Exposure waterfall

For a selected period, UCH derives:

`opening exposure + observed inflows - observed cash recoveries - observed legal recoveries = closing exposure`

The API independently reads the latest immutable projection at the start and end of the period and reports any reconciliation difference. Each currency is a separate series. UCH does not consolidate currencies until the bank supplies and approves its reporting-currency conversion controls.

The same response compares ledger closing exposure with the current balances of the linked authoritative `credit_accounts`. A difference remains visible until the bank's controlled operational account update and case evidence agree; the case ledger never silently rewrites the loan book.

## Production deployment

The base additive migration is `migrations/0030_npl_case_ledger.sql`. Decision governance is added by `migrations/0031_npl_decision_governance.sql`, which expands the immutable event vocabulary and creates the controlled proposal register. Apply both only through the production schema-change procedure after backup verification and before deploying application code that exposes the workspace.
